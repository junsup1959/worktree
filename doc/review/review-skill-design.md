# Review Skill Design — 간결한 MVP와 입력 모드 라우팅

> 상태: Skill 구현 전 설계안  
> 대상: 프로젝트 단위 코드 리뷰 Skill  
> 목표: BDD Skill처럼 짧은 공통 지침만 주입하고, 입력 모드에 맞는 reference만 선택한다.

## 1. 결론

Review Skill은 리뷰 절차를 강제하는 실행 엔진이 아니다. LLM이 주어진 코드와 기준선에서
결점, 논리 오류, 위험을 판단하도록 돕는 **간결한 프롬프트와 조건부 reference 묶음**이다.

MVP는 다음 세 가지에 집중한다.

- 입력을 `git`, `worktree`, `file`, `patch`, `state` 모드로 구분한다.
- 공통 결점 MVP를 기준으로 코드의 발동 조건과 관찰 가능한 영향을 찾는다.
- 사용한 근거와 보지 못한 범위를 함께 보고한다.

다음 항목은 MVP에서 제외한다.

- Coverage Manifest 같은 범위 계약과 필수 스키마
- 단계별 실행 순서, 품질 게이트, 완료 판정
- finding 형식의 기계적 강제
- 범위 수집·검증을 강제하는 스크립트
- 모든 입력 모드의 설명을 한 번에 주입하는 거대 프롬프트

코드의 API·스키마·동작 호환성은 여전히 리뷰 대상이다. 다만 이것을 **Skill 실행 계약**이나
기계적 통과 조건으로 만들지 않는다.

## 2. 컨텍스트 설계

BDD Skill의 장점은 필요한 판단 기준만 짧게 제공한다는 점이다. Review Skill도 같은 밀도를
목표로 한다.

- `SKILL.md`에는 목적, 입력 모드 선택, 공통 결점 MVP, 증거 보고 원칙만 둔다.
- 모드별 명령, 기준선 해석, 한계와 예시는 `references/`로 분리한다.
- 한 요청에서는 필요한 reference만 읽는다. 관련 없는 모드 문서는 읽지 않는다.
- `SKILL.md`와 각 reference는 각각 200줄 이하를 목표로 한다.
- 설명보다 짧은 판단 질문과 작은 예시를 우선한다.
- 동일한 내용을 `SKILL.md`와 reference에 중복하지 않는다.

### 간결한 리뷰 컨텍스트

리뷰를 시작할 때 다음 정도의 짧은 요약만 유지한다.

```yaml
mode: worktree
target: current changes
baseline: HEAD and repository behavior
focus: changed public API and failure paths
limits: untracked binary contents not inspected
```

이는 검증할 스키마가 아니라 LLM의 주의를 정렬하는 메모다. 알 수 없는 항목은 추정하지
않고 생략하며, 파일별 해시나 전체 인벤토리를 기본 컨텍스트에 계속 보관하지 않는다.

## 3. 입력 모드와 reference 라우팅

입력 모드는 고정 절차가 아니라 **어떤 컨텍스트를 추가로 읽을지 정하는 신호**다. 하나의
요청에 여러 신호가 있으면 필요한 reference를 조합할 수 있다.

| 사용자 입력 신호 | 모드 | 읽을 reference | 주로 확인할 것 |
| --- | --- | --- | --- |
| 커밋, 브랜치, 태그, revision range | `git` | `references/git.md` | base 선택, 변경 의미, 회귀와 호환성 |
| 현재 staged·unstaged·untracked 변경 | `worktree` | `references/worktree.md` | 현재 작업 트리 전체와 HEAD의 차이 |
| 두 worktree 또는 두 디렉터리 | `worktree` | `references/worktree.md` | 양쪽 결과물의 추가·삭제·동작 차이 |
| 단일 파일, 파일 목록, 파일·디렉터리 A/B | `file` | `references/file.md` | 선택된 파일의 현재 상태 또는 직접 비교 |
| 제공된 diff나 patch만 있음 | `patch` | `references/patch.md` | hunk 안의 후보와 주변 컨텍스트 부족 |
| 변경 집합 없이 패키지·저장소 상태 검토 | `state` | `references/state.md` | 현재 상태의 명백한 결점과 구조적 위험 |

`references/baseline.md`는 독립 모드가 아니라 필요한 경우 겹쳐 읽는 판단 축이다.

- 비교 기준점이 모호하거나 여러 개일 때
- 요구사항, 테스트, 공개 API, 스키마 같은 행동 기준이 중요할 때
- 기준선이 없어 회귀가 아닌 현재 상태만 판단해야 할 때

모드 판별이 명확하면 사용자에게 형식적인 확인을 요구하지 않는다. 기준선 선택이 결과를
크게 바꾸는데 저장소에서도 확인할 수 없을 때만 짧게 질문한다.

## 4. 리뷰 결점 MVP

공통 본문에는 아래 범주와 핵심 질문만 둔다.

| 범주 | 핵심 질문 |
| --- | --- |
| 정확성·논리 | 현실적인 입력에서 잘못된 분기, 계산, 경계값, 순서가 있는가? |
| 호환성 | 공개 API, 타입, 스키마, CLI, 설정 기본값의 소비자가 깨지는가? |
| 실패·복구 | 중간 실패가 부분 상태, 정리 누락, 비멱등 재시도를 남기는가? |
| 상태·동시성 | 상태 전이, 원자성, 경쟁 조건, 중복 실행이 안전한가? |
| 보안 | 신뢰하지 않는 입력이 주입, 경로 탈출, 권한 우회, 비밀 노출로 이어지는가? |
| 데이터 무결성 | 데이터가 손실, 중복, 오염되거나 정밀도·인코딩이 깨지는가? |
| 자원·성능 | 입력 규모에 따라 시간, 메모리, 핸들, 쿼리 비용이 비정상적으로 커지는가? |
| 설정·운영 | 플랫폼, 권한, 환경 변수, 배포·복구 조건에서 실패하는가? |

`references/review-mvp.md`에는 다음과 같은 조건부 관점과 예시만 둔다.

- 테스트와 관측 가능성
- UI 접근성과 오류 피드백
- locale, timezone, Unicode, 플랫폼 차이
- 개인정보, 로그, 보존·삭제 정책
- 의존성, 설치 훅, 빌드와 공급망

조건부 관점은 변경 신호가 있을 때만 읽거나 적용한다. 모든 리뷰에서 체크리스트를 형식적으로
나열하지 않는다.

## 5. Finding 판단과 보고

Finding은 다음 내용을 설명할 수 있을 때 보고한다. 이것은 출력 계약이나 탈락 게이트가
아니라, 근거 없는 추측을 줄이는 판단 질문이다.

- 어디에서 어떤 입력이나 상태로 문제가 발생하는가?
- 사용자가 관찰할 수 있는 잘못된 결과나 위험은 무엇인가?
- 코드, 테스트, 요구사항 또는 안전 불변식 중 무엇이 판단을 뒷받침하는가?
- 주변 validation이나 호출자가 문제를 막고 있지는 않은가?
- 어떤 테스트, 재현 또는 정적 추적으로 확인할 수 있는가?

스타일 선호, 발동 조건이 없는 가능성, 중복 항목은 finding으로 만들지 않는다. 증거가
부족하지만 중요한 위험은 확정 결점이 아니라 한계나 잔여 위험으로 표현한다.

권장 출력은 고정 양식보다 짧은 findings-first 보고다.

```markdown
## Findings
- [High] `path/file.py:123` — 실패 후 일부 상태가 남는다.
  - 조건/영향: 두 번째 쓰기 실패 시 첫 번째 파일만 갱신된다.
  - 근거/확인: rollback이 없으며 실패 주입 테스트로 확인할 수 있다.

## Review notes
- 기준선: HEAD와 기존 테스트
- 확인 범위: 변경 API, 호출자, 실패 경로
- 한계: Windows 권한 실패는 실행 재현하지 못함
```

Finding이 없으면 “확인한 범위에서 검증 가능한 결점을 찾지 못했다”고 말한다. 전체 코드에
결함이 없다고 확대 해석하지 않는다.

## 6. Graphify 사용

`graphify-out/graph.json`이 있으면 영향 범위를 좁혀 찾는 데 사용한다.

- 변경 심볼과 관련된 호출자, 테스트, 설정, 실패 경로를 찾는다.
- 넓은 관계는 `query`, 특정 연결은 `path`, 한 개념은 `explain`으로 확인한다.
- 결과의 실제 소스를 열어 관계와 동작을 검증한다.
- 그래프 관계 자체를 버그 증거로 사용하지 않는다.
- 그래프가 없거나 결과가 부족하면 좁은 검색과 직접 소스 추적으로 대체한다.

Graphify는 모든 리뷰에서 따라야 하는 단계가 아니라, 추가 컨텍스트의 가치가 있을 때 쓰는
확장 수단이다.

## 7. 제안하는 Skill 구조

```text
skills/review/
  SKILL.md
  agents/
    openai.yaml
  references/
    git.md
    worktree.md
    file.md
    patch.md
    state.md
    baseline.md
    review-mvp.md
```

- `SKILL.md`: BDD Skill과 비슷한 밀도의 공통 프롬프트와 reference 선택 안내
- 모드 reference: 해당 입력에서 필요한 수집 관점, 비교 기준, 대표 한계
- `baseline.md`: 기준선의 종류와 기준선이 없을 때 주장 범위
- `review-mvp.md`: 조건부 결점 관점과 짧은 finding 예시

MVP에는 `scripts/`를 만들지 않는다. 이후 스크립트가 필요해도 컨텍스트 축약, 입력 라우팅,
반복적인 정보 수집을 돕는 범위로 제한한다. 스크립트가 finding 채택, 심각도, 완전성,
출력 형식을 결정하거나 계약을 강제해서는 안 된다.

## 8. SKILL.md의 목표 밀도

최종 `SKILL.md`는 다음 네 부분이면 충분하다.

1. 리뷰 목적: 코드의 검증 가능한 결점과 위험을 찾는다.
2. 입력 모드: 신호에 맞는 reference 하나 또는 필요한 조합만 읽는다.
3. 결점 MVP: 정확성, 호환성, 실패, 상태, 보안, 데이터, 자원, 운영을 본다.
4. 증거 보고: 위치, 발동 조건, 영향, 근거, 확인 방법과 한계를 짧게 남긴다.

이 범위를 넘는 모드별 명령, 긴 예시, 조건부 도메인 지식은 본문에 추가하지 않고 reference로
보낸다. 목표는 리뷰를 자동 절차로 바꾸는 것이 아니라, 작은 컨텍스트로 LLM의 판단 품질을
높이는 것이다.
