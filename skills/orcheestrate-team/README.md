# Orcheestrate Team 오케스트레이션 안내서

이 문서는 `orcheestrate-team` Skill의 구성과 실행 방식을 한글로 설명한다.
사람이 구조를 이해하기 위한 안내서이며, 새로운 실행 계약을 추가하지 않는다.
실제 동작 규칙의 기준은 [SKILL.md](SKILL.md), 역할별 에이전트 설정, 실행 중인
저장소 지시문과 사용자의 요청이다. 서로 충돌할 때는 상위 지시와 실제 런타임
권한을 우선한다.

## 목적

`orcheestrate-team`은 구현 작업을 고정된 5인 팀으로 나누어 수행하기 위한
오케스트레이션 Skill이다. PM이 모든 메시지와 작업을 중계하는 방식이 아니라,
아키텍처와 범위는 PM이 통제하고 일상적인 작업 배정과 진행 관리는 PL이
담당한다.

이 Skill은 범용 워크플로 엔진을 만들지 않는다. 작업 순서와 의존성을 설명하는
가벼운 Task DAG와 자연어 메시지만 사용하며, 큐, 임대(lease), 데이터베이스,
상태 머신, 보상, 자기 평가·학습 루프 같은 실행 체계는 도입하지 않는다.

## 팀 구성

팀은 다음 5개 역할로 고정된다.

```text
사용자
  │
  ▼
PM ── 아키텍처·범위·팀 구성 결정
  │
  ▼
PL ── Task DAG 작성·작업 배정·진행 조정
  ├──────────────┐
  ▼              ▼
Developer 1    Developer 2
  └──────┬───────┘
         ▼
        QA ── 독립 검토·검증
         │
         └── 결과를 PL에 전달
```

| 역할 | 구성 | 주요 책임 | 기본 권한 |
| --- | --- | --- | --- |
| PM | Skill을 호출한 주 에이전트 | 아키텍처, 범위 해석, 팀 감독, 최종 응답 | 현재 세션 권한 |
| PL | `orcheestrate-team-pl` | Task DAG, 작업 배정·재배정, QA 인계 | 읽기 전용 |
| Developer 1 | `orcheestrate-team-developer` 첫 번째 인스턴스 | PL이 배정한 구현 노드 수행 | 작업공간 쓰기 |
| Developer 2 | `orcheestrate-team-developer` 두 번째 인스턴스 | PL이 배정한 구현 노드 수행 | 작업공간 쓰기 |
| QA | `orcheestrate-team-qa` | 완료 노드의 독립 검토와 검증 | 읽기 전용 |

두 개발자는 서로 다른 에이전트 프로필을 만들지 않는다. 동일한 개발자
프로필을 서로 다른 안정적인 작업 이름으로 두 번 생성하고, 시작 프롬프트에서
Developer 1과 Developer 2의 런타임 정체성을 구분한다.

권장 모델과 추론 강도는 다음과 같다.

| 역할 | 모델 | 추론 강도 |
| --- | --- | --- |
| PL | `gpt-5.6-luna` | `high` |
| Developer 1·2 | `gpt-5.6-terra` | `medium` |
| QA | `gpt-5.6-luna` | `high` |

이 값은 저장소의 사용자 정의 에이전트 프로필에 기록된 선호 설정이다. 실제
실행 환경이 모델, 추론 강도 또는 샌드박스 설정을 재정의하면 런타임 설정이
우선하며, 적용되지 않은 프로필이나 권한을 적용되었다고 간주하지 않는다.

## 역할별 권한 경계

### PM

- 사용자 요청을 해석하고 아키텍처와 범위의 기준을 정한다.
- 아키텍처나 범위가 바뀌면 PL, 두 개발자, QA 모두에게 같은 결정을 전달한다.
- 구조, 범위, 팀 구성에 영향을 주는 에스컬레이션을 결정한다.
- 최종 저장소 상태와 Final Completion Audit 결과를 확인해 사용자에게 하나의
  결과로 보고한다.

PM은 일상적인 개발자·QA 메시지의 중계자가 아니다.

### PL

- PM의 방향을 실행 가능한 Task DAG로 나눈다.
- 의존성이 충족된 노드만 개발자에게 배정한다.
- 개발자 한 명에게 동시에 하나의 구현 노드만 맡긴다.
- 같은 파일이나 공용 인터페이스를 동시에 수정하지 않도록 소유권과 순서를
  조정한다.
- 개발 완료 노드를 QA에 넘기고, QA 결과에 따라 수정 작업을 다시 배정한다.
- 모든 노드 판정 뒤 같은 QA에게 전체 변경의 Final Completion Audit을 요청한다.

실행 가능한 개발 작업을 새로 만들거나 변경할 권한은 PL에게만 있다. PL은
아키텍처 변경을 제안할 수 있지만 승인하지는 않는다.

### Developer 1·2

- PL이 배정한 현재 노드만 구현한다.
- 수정 전 관련 저장소 지시, 의존성, 타입과 인터페이스를 확인한다.
- 새 작업이나 범위 변경을 발견해도 스스로 배정하지 않고 PL에 보고한다.
- 공용 영역이 겹칠 때만 다른 개발자와 직접 조정한다.
- QA 검토 중에는 재현 방법과 증거를 QA와 직접 논의할 수 있다.

QA가 결함을 발견해도 개발자가 즉시 독자적으로 수정 범위를 만들지는 않는다.
PL이 교정 작업을 명시적으로 배정한 뒤 수정한다.

### QA

- PL이 인계한 완료 노드와 최종 통합 결과를 독립적으로 검토한다.
- 구현 설명에 의존하지 않고 코드, 테스트, 경계 조건과 회귀 위험을 직접
  확인한다.
- 최종 감사에서는 사용자 의도, 산재된 문제, 향후 실패 가능성, 교차 파일·설정·
  호출부·통합 영향을 별도로 확인하고 검증하지 못한 범위를 밝힌다.
- 검토 중인 개발자에게 증거나 재현 정보를 직접 물을 수 있다.
- 결과와 근거를 PL에게 전달한다.

QA는 수정 작업을 권고할 수 있지만 생성하거나 배정하지 않는다. 아키텍처나
범위 문제는 PL을 거쳐 PM에 에스컬레이션한다.

## Task DAG

Task DAG는 PL이 관리하는 간결한 Markdown 작업 메모다. 기계가 소비하는 상태
계약이 아니므로 필요한 정보만 기록한다.

```markdown
- T1 - 공용 인터페이스 정의
  - 의존성: 없음
  - 담당: Developer 1
  - QA 초점: 호환성과 호출부 누락
- T2 - 어댑터 구현
  - 의존성: T1
  - 담당: T1 검토 전까지 미배정
  - QA 초점: 오류 경로와 통합 동작
```

각 노드에는 안정적인 짧은 ID, 구체적인 작업 범위, 의존성, 준비된 경우의
담당 개발자, 구현 후 QA가 볼 검증 초점을 포함한다. 구현 증거로 계획을
바꿔야 할 수 있지만, 아키텍처나 범위까지 달라지면 PM의 결정을 먼저 받는다.

## 실행 흐름

1. **기준 설정**  
   PM이 요청과 저장소 지시를 확인하고 아키텍처 기준을 세운 뒤 PL,
   Developer 1, Developer 2, QA를 정확히 한 명씩 만든다.

2. **계획 정렬**  
   PL이 누락된 의존성, 공용 쓰기 영역과 검증 기준을 점검해 Task DAG를
   작성한다. PM은 아키텍처 수준의 질문을 결정한다.

3. **준비된 노드 배정**  
   PL이 의존성이 충족된 노드를 개발자별로 하나씩 배정한다. 독립적인 노드는
   병렬로 수행하고, 같은 파일이나 공용 인터페이스를 건드리는 노드는
   직렬화하거나 명시적으로 소유권을 나눈다.

4. **공용 영역 조정**  
   개발자가 겹침을 발견하면 다른 개발자와 PL에 알린다. PL이 소유권이나
   순서를 확인한 뒤 정해진 범위에서 계속한다.

5. **노드별 QA**  
   개발자가 변경 내용과 실제 검증 증거를 PL에 제출한다. PL이 QA에
   인계하고, QA는 수용 가능, 교정 필요, 아키텍처·범위 에스컬레이션 중 하나의
   자연어 결론과 근거를 돌려준다.

6. **다음 노드 또는 최종 감사**
   PL이 QA 결과에 따라 다음 의존 노드를 열거나 교정 작업을 배정한다. 모든
   범위 내 노드가 QA 검토를 받으면 같은 QA에게 전체 변경과 사용자 요청을
   넘겨 Final Completion Audit을 수행한다.

7. **최종 보고**
   PM은 감사 근거로 `사용자 의도 충족 여부`, `남아 있는 문제와 잠재 위험`,
   `검증 범위와 한계`, `최종 QA 판정`을 보고한다. 잔여 문제가 발견되지 않은
   경우에도 검사 범위와 근거 없이 단순히 “완료”라고 하지 않는다.

## 에이전트 간 통신

| 경로 | 용도 |
| --- | --- |
| PM → PL | 아키텍처, 구현 기준, 감독, 에스컬레이션 결정 |
| PM → 전원 | 승인된 아키텍처 또는 범위 변경 알림 |
| PL → 개발자 | 준비된 노드의 작업 배정과 조정 |
| PL → QA | 완료 노드의 검토와 전체 변경의 최종 감사 인계 |
| 개발자 ↔ 개발자 | 기존 배정의 공용 영역·의존성 조정 |
| 개발자 ↔ QA | 진행 중인 검토의 증거·재현 논의 |
| 개발자·QA → PL | 완료 결과, 발견 사항, 장애물, 검토 결론 |

직접 대화는 이미 배정된 작업의 협업 수단이다. 새로운 작업을 만들거나
우선순위를 바꾸는 권한은 생기지 않는다.

협업 도구는 의도에 따라 사용한다.

- `spawn_agent`: 팀원을 만들고 첫 작업을 즉시 시작한다.
- `send_message`: 실행 중이거나 존재하는 팀원에게 정보를 전달한다.
- `followup_task`: 유휴 팀원에게 후속 작업을 주어 새 턴을 시작한다. 실행
  작업을 만들거나 바꾸는 용도로는 PL만 사용한다.
- `wait_agent`: 실행 중인 작업의 새 소식을 기다린다.
- `list_agents`: 고정된 팀 구성과 현재 상태를 확인한다.
- `interrupt_agent`: 더 이상 필요하지 않거나 위험·방향 전환으로 중단해야
  하는 현재 턴만 멈춘다.

에이전트의 한 턴이 완료되면 실행 중인 작업은 끝나지만, 해당 에이전트 핸들은
후속 메시지를 받을 수 있도록 남을 수 있다. 목록에 완료 상태로 보이는 것은
실행이 계속되고 있다는 뜻이 아니다. 정상 완료한 에이전트를 단지 목록에서
없애기 위해 중단하지 않는다.

## 실패와 에스컬레이션

- 역할 하나를 만들 수 없다고 다른 역할이 대신하거나 임의의 인원을 추가하지
  않는다.
- 개발 중 파일이나 인터페이스 소유권이 겹치면 두 개발자가 경쟁 수정하지
  않고 PL이 순서를 다시 정한다.
- QA의 교정 요청은 PL이 새 범위로 배정한 뒤 개발자가 수행하고 QA가 다시
  확인한다.
- 같은 문제가 반복되거나 구조 문제로 드러나면 PL이 PM에 에스컬레이션한다.
- 작업이 대체되었거나 위험하거나 범위가 바뀐 경우에만 아직 실행 중인 턴을
  중단한다.

## 하지 않는 것

- PM·PL·개발자·QA 외의 역할을 자동으로 추가하지 않는다.
- 작업이 느리다는 이유로 개발자 수를 늘리지 않는다.
- 자연어 협업을 강제 JSON 메시지나 상태 코드로 바꾸지 않는다.
- 피어 메시지로 PL의 작업 배정 권한을 우회하지 않는다.
- 에이전트 내부 대화를 그대로 최종 사용자 응답에 노출하지 않는다.
- 계획 전용 또는 읽기 전용 요청에서 실제 수정이나 테스트를 수행했다고
  주장하지 않는다.
